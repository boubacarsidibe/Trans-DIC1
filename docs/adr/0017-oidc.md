# ADR 0017 : connexion unique OIDC avec le fournisseur d'identité de l'EPT

- Statut : accepté (validation du fournisseur réel avec le CRI à faire)
- Date : 2026-10-31
- Tâche : ARCH-09 (#73)
- Précise : ADR 0005 (jetons et renouvellement)

## Contexte

Les comptes Trans-DIC1 sont aujourd'hui locaux : l'administrateur les crée, chaque agent garde un
mot de passe de plus. L'EPT veut que le personnel se connecte avec son compte de l'école, que le
départ d'un agent coupe aussi son accès à la supervision, et que les rôles se gèrent au même endroit
que les autres applications.

Contraintes :

- le fournisseur du CRI n'est pas encore choisi ni ouvert à l'équipe (Keycloak est le plus
  probable, mais Azure AD/Entra ou un autre fournisseur OIDC restent possibles) ;
- la connexion locale doit rester disponible tant que le fournisseur n'est pas validé, et ensuite
  comme accès de secours (compte de bootstrap) ;
- aucune dépendance de plus côté écran si possible (surface d'attaque, poids du bundle).

## Options

| Option | Pour | Contre |
|---|---|---|
| A. Backend en client confidentiel (`oauth2-client`, session serveur) | secret côté serveur, jetons jamais dans le navigateur | casse le modèle sans état de l'ADR 0005 ; session collante ou partagée entre répliques ; deux modes d'authentification très différents |
| B. Écran en client public (Authorization Code + PKCE), backend en serveur de ressources | même modèle que l'ADR 0005 (jeton court en mémoire, en-tête Bearer) ; backend sans état ; standard (RFC 7636, OAuth 2.0 for Browser-Based Apps) | jeton de renouvellement du fournisseur en mémoire dans le navigateur |
| C. Bibliothèque côté écran (keycloak-js, oidc-client-ts) | moins de code | dépendance de plus ; keycloak-js lie au seul Keycloak |

## Décision

Option B, sans bibliothèque :

- l'écran lit `GET /api/v1/auth/configuration` et affiche « Se connecter avec le compte EPT » quand
  `auth.oidc.enabled=true` ;
- flux Authorization Code avec PKCE S256, `state` et `nonce` ; le vérificateur ne vit que le temps de
  l'aller-retour (sessionStorage, effacé au retour sur `/auth/callback`) ;
- les jetons restent en mémoire comme pour la connexion locale ; le renouvellement passe par le
  `refresh_token` du fournisseur, la déconnexion ferme aussi la session du fournisseur
  (`end_session_endpoint`) ;
- le backend valide chaque jeton (signature par les clés publiques du fournisseur, émetteur,
  expiration) puis convertit les rôles : `realm_access.roles`, `resource_access.<client>.roles` ou
  groupes, noms configurables (`trans-dic1-admin`, `-noc`, `-viewer`). Le plus fort l'emporte ; sans
  rôle connu, la requête est refusée (401) ;
- à la première connexion, un compte local est créé (même nom, courriel du jeton, mot de passe
  aléatoire inutilisable) pour que l'audit, les affectations d'alertes et les vues fonctionnent sans
  changement ; son rôle suit le fournisseur à chaque requête ;
- la connexion locale reste ouverte par défaut (`auth.local.enabled=true`) ; l'exploitation peut la
  fermer une fois le fournisseur validé.

Pour développer et tester sans le CRI, un Keycloak est fourni dans `docker-compose.yml` (profil
`sso`) avec un royaume importé : client public `trans-dic1-web`, trois rôles, trois comptes de
démonstration à mot de passe temporaire.

## Conséquences

- Établi : jetons du fournisseur acceptés et convertis, rôle mis à jour, jeton sans rôle refusé,
  connexion locale préservée ou fermée (tests `OidcAuthTests`, `OidcOnlyLoginTests`) ; PKCE vérifié
  sur le vecteur de la RFC 7636, échange du code, refus d'un `state` inattendu, renouvellement et
  déconnexion (tests `oidc.test.js`).
- Non établi : le comportement avec le fournisseur réel de l'EPT (noms des rôles, présence de
  `preferred_username`, durée des sessions). C'est l'étape de validation avec le CRI, décrite dans
  `docs/devops/connexion-unique.md`.
- Un jeton volé côté navigateur reste utilisable jusqu'à son expiration (5 min conseillées) : même
  risque et même parade (CSP, pas de stockage persistant) que l'ADR 0005.
- Un compte supprimé chez le fournisseur ne peut plus obtenir de jeton ; son compte local reste pour
  l'historique et peut être désactivé dans Trans-DIC1.
